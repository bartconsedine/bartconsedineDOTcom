# Calendar companion

Private enhanced Google Calendar client at `/admin/apps/calendar-companion`: a combined calendar, family birthdays, sitter booking queue, planning suggestions, and configurable planning rhythm. Registered through the normal protected app registry and shared API dispatcher.

## Source of truth and sharing

The user explicitly requested **Google Calendar as the event source of truth**. Google owns event dates, yearly birthdays, notes, sitter status, coverage windows and booking nudges. The app reads directly from Google on load/refresh and writes directly to its API. No event replica, authoritative snapshot, birthday table, calendar export/import sync, or browser storage is used. The existing `model.js` planner shape is a disposable calculation projection, never the persisted event store.

Every new plan, family birthday, sitter entry and booking nudge goes to the connected account's **personal primary Google calendar**. Google identifies that calendar; the app never guesses by display name or falls back to another writable calendar. It is always included in reads. Up to four other calendars may be included for viewing and availability checks; this app does not write to them. A legacy `writeCalendar` preference cannot redirect writes. Google Calendar's existing ACLs govern sharing of your personal events; the app does not create or broaden ACLs. Its server verifies the workspace admin independently, binds the provider access token to that same verified Google subject/email, lists accessible calendars and checks that the destination is the personal primary calendar with a writer/owner role before writing. Read-only and externally managed events can be viewed here and opened in Google; the app editor changes only companion-managed plans/birthday series.

Supabase `public.app_data` persists only private preferences/ideas: slug `calendar-companion`, key `google-v2`, version 2. Fields are `settings`, `ideas`, `readCalendars` (up to five), and `writeCalendar`. The reviewed contract rejects events, birthdays, ownership fields and tokens. Both admins have separate preferences under existing owner RLS. Browser and trusted chat preference writes use atomic revision checks. No schema, membership, new credential or secret changes are required. The superseded unshipped `planner-v1` snapshot is never treated as Google events or automatically uploaded; any old recovery draft must be reconciled explicitly.

## Connection, permissions and expiry

“Connect Google Calendar” performs a protected same-origin POST, then starts the existing Supabase Google OAuth PKCE flow with incremental scopes:

- `https://www.googleapis.com/auth/calendar.calendarlist.readonly`
- `https://www.googleapis.com/auth/calendar.events`

Normal workspace sign-in is unchanged. The existing `/auth/callback` redirect URL stays unchanged. A ten-minute HttpOnly navigation cookie selects only the fixed calendar return path and is cleared after successful sign-in; unknown values fall back to `/admin`. No new redirect allowlist entry or open redirect is introduced. Auth/verified Google identity and live enrollment checks remain in the callback, registry, API dispatcher and Supabase data helpers. Provider access tokens stay in the existing HttpOnly auth session and server requests; they are never sent to the app component, logged, or written to ordinary app records. Google userinfo must match the independently verified admin subject and email before every calendar operation. Session data retrieves a credential; it does not authorize workspace access.

This deliberately requests online access and has no refresh-token store or unattended Google worker. Supabase does not refresh provider access tokens. Missing/expired access or lost consent leads to an explicit reconnect state; Google events/reminders already saved remain in Google. The real consent flow has not been exercised during development. The existing Google OAuth project's Calendar API must be enabled and consent/testing policy must permit these scopes/accounts; missing setup surfaces as an error. Configure this through the normal Google project administration process, not by putting credentials into app data. No consent, API enabling, ACL, or credential change was performed by this PR.

## Google event behavior

- Read selected calendars with full pagination, expanded recurring instances and Google IDs/etags. The personal primary calendar is mandatory; additional calendars are optional availability sources. The view loads the planning year plus the visible grid, merging overlapping ranges and deduplicating disjoint results (at most two intervals, with a 2,500-event limit per calendar/interval); incomplete reads fail visibly and disable writes/planning. Calendar choices remain available to recover a lost or overfull selection. Refresh explicitly after external edits; there is no webhook or live subscription.
- Create **regular Google all-day yearly events** for birthdays, with month/day, family member name and optional gift/celebration notes. A birth year is not required; recurrence starts in 2000 so the next occurrence exists regardless of the current year. February 29 uses the last day of February each year. Notifications are popup overrides approximately 14, 7 and 1 days before, at 09:00 in the calendar's zone. This does not create Google Contacts or alter Contacts' native birthday calendar. Existing native birthday events are displayed too. Birthday edits fetch the recurring master and explicitly edit the whole series using its etag.
- Plans store companion fields in Google `extendedProperties.shared`: kind, stable group ID, coverage, sitter name, booking lead and buffer. The separate sitter entry covers the plan plus its buffer. Unresolved coverage gets a transparent daily recurring Google reminder with a popup at its start, ending before the plan begins. Native Google notification settings determine delivery when the website is closed; the app sends no email, SMS or sitter outreach.
- Coverage changes update the Google plan and reconcile its linked entries. Resolving nudges removes recurrence/notifications and retains one quiet transparent resolution marker, rather than deleting the ID; reopening coverage updates the same ID. The app does not silently recreate user-deleted linked events: restore them from Google trash and repair. Companion support entries are generated from the parent plan; edit the parent for coverage changes.
- Plan/coverage/reminder writes are separate Google operations, not a transaction. A partial failure returns `saved: true, supportSynced: false` with a repair warning. The UI distinguishes the confirmed plan from incomplete support entries. “Repair linked entries” on the plan editor or sitter queue recomputes them from the saved Google plan; it does not apply unsaved form edits. Refresh and repair after moving a plan directly in Google. Parent etags are checked again after reconciliation to surface concurrent changes.
- Edits use Google `If-Match` with the version fetched for editing. Stale writes fail without silently replacing newer Google data. Creates use deterministic per-owner/request IDs, preserving request identity while a form is open; an uncertain retry returns the matching event or rejects differing details instead of creating duplicates. Google error/timeout bodies never expose credentials. Redirects are disabled for credential-bearing API calls.
- Suggestions count companion plans toward the weekly goal and avoid opaque timed/all-day busy events across selected calendars, including sitter buffers. Before a new/moved plan is saved, the server checks Google's current availability again. Resolving coverage on an unchanged date remains possible if a new conflict appeared. This is a best-effort availability check, not a cross-calendar reservation lock. “Fill open slots in Google” saves planning holds sequentially, reports confirmed counts and stops on the first unconfirmed/partially reconciled write. It does not book venues or contact sitters.

Loading, consent-needed, stale-read, empty, working, confirmed-save, conflict and repair states are explicit. Failed forms remain recoverable and downloadable with current preferences/revision. Downloaded JSON is a recovery transfer, not authoritative storage or a blind import mechanism. Event creation is disabled while preferences are unsaved or Google reads fail.

## Chat maintenance

Use `docs/CHAT_APP_DATA.md` and `.agents/skills/app-data/SKILL.md` for user-requested **preferences and ideas** only:

```sh
node scripts/app-data-sql.mjs read calendar-companion bartconsedine@gmail.com
node scripts/app-data-sql.mjs write calendar-companion bartconsedine@gmail.com /private/tmp/calendar-preferences-change.json
```

The private 0600 transfer file must contain exactly `value` (complete validated preferences) and `expectedAt` (latest exact revision, null only for creation). Use the unchanged generated SQL through the verified Supabase connector, require save authorization/confirmation, reread, and preserve unrelated fields. Runtime credentials/owner privileges must never be exposed to the browser. Chat event/birthday changes use the authenticated Google Calendar connector and live Google event IDs/versions, never SQL or a fabricated Supabase event copy. The chat connector's Google grant is separate from the website's OAuth consent.

## Verification and release

Use Node 22.23.2 and `npm run db:validate`, `npm test`, `npm run build`. Tests cover preference contract/owner RLS and revisions, Google identity binding/redirect allowlist, native and managed birthdays, leap/year boundaries, recurring-master edits, transport pagination/auth/If-Match, idempotent creates, selected-calendar conflict checks, coverage reopen/resolve, partial writes and repair, permission denial, expired consent, CSRF, input limits and recoverable UI failures. Google behavior is tested with a fake remote/API transport; real PostgreSQL via PGlite verifies private preference persistence and second-owner denial. Static browser fixtures render the actual component with explicitly synthetic Google events at desktop/phone widths; handler tests execute its real JSX/event handlers separately.

Hosted consent, live Google read/create/edit/reload from a fresh session, a second household Google account, actual device notification delivery and deployed browser QA remain unverified until the authorized rollout and user consent. No real Google or hosted database records were written during development. This PR remains stacked on #12's guarded app-data infrastructure; merge that dependency and recheck the retargeted PR before authorized release.
