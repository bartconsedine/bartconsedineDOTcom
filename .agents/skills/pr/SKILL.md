# Change, review, and verify the release

Treat `/pr` in a task request as the user's name for this workflow, not as a registered slash command. The explicit Codex skill invocation is `$pr`; `/skills` is the CLI picker. If the skill has not been discovered, read this file directly. See [contributor guidance](../../../CONTRIBUTING.md).

## Deliver a reviewable change

1. Inspect current state before editing: read repository instructions, check status/remotes/worktrees, fetch the intended base, and inspect recent/open PRs so already merged work is preserved. Start a clean branch from latest remote `main` unless the task specifies another base. Preserve user changes and existing worktrees. For Mac checkouts, use a verified local-only directory outside synced Documents/iCloud when cloud placeholders make files unreliable; verify files are readable before installing dependencies. Do not work directly on `main`.
2. Make the smallest change that satisfies the requested scope. Prefer existing GitHub validation and Vercel Git deployments; avoid new runners, dependency changes, local containers, or release scripts unless the task needs them. UI tasks do not authorize database/auth setup. Inspect all affected UI surfaces and preserve actions, destinations, and accessible labels. Document every change in the PR: the problem, resulting behavior, and reason for the approach. Update durable repository documentation when behavior, setup, configuration, schema, operations, or contributor workflow changes; include examples and recovery steps when useful.
3. Add or update meaningful tests for every functionality change, including regressions and security boundaries where relevant. A bug fix should demonstrate the failure it prevents. Cover success and denial/error paths, not just implementation wording. For documentation-only changes, validate links, instructions, examples, and skill metadata; explain why runtime test additions are not applicable. Do not add tautological tests merely to satisfy a file-count rule.
4. Run the applicable checks below against the final diff. Record actual commands, results, environment, and untested limits. Fix failures before declaring readiness. If credentials or services block validation, report the precise blocker and keep the affected claims unverified; do not invent successful results or bypass the check.
5. Review the complete diff for unrelated changes, credentials, authorization regressions, and documentation/test gaps. Create or update a draft PR using the repository template. Attach the PR to the task when the tool is available. Include exact validation evidence and any remaining setup or deployment steps.
6. Capture the final PR head SHA and verify GitHub CI/checks for that exact head (a workflow may expose a PR merge SHA; verify its association with the current head). Pending/stale checks are not green. Review the final diff and resolve failures before marking ready. Any additional push invalidates the prior check evidence. Prefer `gh pr checks` and existing Actions runs; use a SHA guard such as `gh pr merge --match-head-commit <head-sha>` for an authorized merge. Never bypass protections or use an admin override. Existing explicit user merge/release authorization is sufficient; invoking this skill alone does not authorize release or hosted schema, credential, or membership changes.
7. After merge, record the actual main merge SHA and the pre-release rollback commit/deployment. Follow the existing Vercel Git deployment for the intended team/project and production environment to Ready. Verify its source commit equals the merge SHA and the production domain points to it; a preview, green PR check, or reachable URL alone does not prove production shipped. Prefer authenticated tools; if their access fails, use an available authenticated CLI or signed-in dashboard for the same target. Do not change project settings or create a manual deployment merely to avoid a failed inspection.
8. Inspect the actual production pages in a browser at desktop and mobile widths, including affected authenticated UI when a session is available. Exercise navigation and relevant controls, inspect visible text/layout/overflow, and capture requested screenshot evidence. App-card branches can be covered by rendered fixtures when the real registry is empty; do not register fake production apps. Distinguish live browser checks from fixture/HTTP checks. Reset temporary viewport overrides. If credentials, CI, deployment, or browser access fails, complete independent work, make one bounded diagnostic/retry where useful, and report the exact remaining blocker without claiming success.

## Applicable checks

Start with the pinned Node version in `.nvmrc` and `npm ci` when dependencies are not already installed for the lockfile. Run `npm run db:validate`, `npm test`, and `npm run build`, as CI does. Add targeted checks based on the change:

- Auth/API changes: both approved accounts, unapproved identity, missing/expired session, confirmed matching verified Google identity, membership denial, cross-user data isolation, and private/no-store responses as applicable.
- Schema or database tooling: fresh installation, upgrade, RLS/grants/functions, and the isolated PostgreSQL backup/restore drill from [the database runbook](../../../docs/DATABASE_MIGRATIONS_AND_BACKUPS.md). Never edit an applied migration. Use only the approved Prisma workflow; a hosted write requires its secure connection and verified pre-migration backup. Membership enrollment remains a separate explicit grant.
- UI or routing: exercise affected public and protected flows. Report whether checks were local, HTTP-only, or browser-based; do not claim a visual review without one.
- Skill/workflow documentation: validate frontmatter and relative links, check commands against current scripts, and walk through representative requests including a failed check or unavailable credential. Record these checks rather than adding tests that assert prose strings.

End with the PR link, tested head and merge SHA, Vercel Ready deployment and matching source SHA, live desktop/mobile evidence (screenshots or verified Library IDs when requested), skill path, rollback target, and remaining blockers. Distinguish code shipped from hosted setup completed.
