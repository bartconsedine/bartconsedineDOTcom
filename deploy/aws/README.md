# Move bartconsedine.com to AWS

Production continues to use Vercel and hosted Supabase until the final data comparison, Google sign-in, private workspace checks and DNS cutover succeed. The migration uses ARM64 Lambda for Next.js, Amazon Cognito Lite for Google sign-in, and a private Aurora PostgreSQL 17.11 writer. The account has a zero Lightsail instance quota. The [earlier single-host rehearsal](lightsail-rehearsal.md) documents a tested database recovery fixture.

## AWS resources

| Stack | Purpose |
| --- | --- |
| bart-site-releases | Private encrypted S3 bucket for immutable, content-addressed site builds and encrypted recovery artifacts |
| bart-site-http | HTTP API with IAM-protected staging and regional custom domains for cutover |
| bart-site-web | ARM64 Node 22 Lambda with seven-day logs and IAM-only invocation during rehearsal |
| bart-site-auth | Cognito user pool, managed login domain and optional Google federation |
| bart-site-database | Encrypted PostgreSQL, no public writer or inbound network rule, IAM-authenticated RDS Data API and seven-day backups |

Aurora is configured for 0–1 ACUs and a five-minute idle timeout. Compute charges stop when it pauses. Storage, managed secrets, I/O and active compute can accrue charges. Avoid persistent database listeners and idle connections. Measure the half-hour cron's effect on active time during acceptance. The older Lightsail monthly estimate does not apply to these stacks. [Aurora auto-pause](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2-auto-pause.html). [Aurora pricing](https://aws.amazon.com/rds/aurora/pricing/).

## Release the site privately

Use the verified site account and us-east-1. Build the reviewed tree with the pinned Node 22 runtime on an ARM64 Linux builder, without production secrets or local environment files. Run `SITE_STANDALONE=1 npm run build` followed by `bash deploy/aws/package-web.sh "$PWD" /absolute/path/site.zip`. Deploy `artifacts.yaml` to the releases stack. Upload the zip under `web/<sha256>.zip` in its Bucket output. Deploy `web.yaml` to the web stack with CAPABILITY_IAM, ReleaseBucket and ReleaseKey. Use a signed Lambda invocation with an HTTP API v2 event to verify the public page, assets and protected denial. Switching the release key to the previous verified object restores that site build. Deploy `http.yaml` to bart-site-http. The default staging route requires an AWS SigV4 request for execute-api. During cutover, verify DNS authority, add an ACM-compatible CAA issuer alongside the other issuers if needed, and validate an ACM certificate covering apex and www. Pass its ARN to the HTTP stack before changing website records. Verify the API mappings, then enable PublicTrafficEnabled and use Route 53 aliases to the regional endpoints. This closes the default API Gateway hostname and serves the custom domains.

## Connect Google

The login page uses the same-origin referrer policy so browsers send the site origin when submitting the Google form, including before JavaScript loads. OAuth callback responses suppress referrers. After deploying, submit the live login form and verify that it redirects to Cognito.

Deploy `cognito.yaml` to the auth stack and read the GoogleRedirect output. In the Google web OAuth client, retain the existing callback and register both the Cognito GoogleRedirect value and `https://bartconsedine.com/auth/calendar/callback`. The second callback grants Calendar permission separately from site login. Download the updated Google client JSON to a private file with mode 0600. Run `python3 deploy/aws/connect-google.py /private/path/google-oauth.json` with the correct AWS profile, or pass an authenticated AWS CLI wrapper with `--aws`. It verifies the target and Cognito callback, checks the Calendar callback, stores the credential in Secrets Manager, and installs the Google provider and code-only client. Keep credentials and OAuth codes out of Git, terminal output and logs.

The site selects Cognito via AUTH_PROVIDER=cognito, SITE_URL, COGNITO_POOL_ID, COGNITO_DOMAIN and COGNITO_CLIENT_ID. The web client ID comes from the auth stack output. Its OAuth grant activates when Google is connected. Provide GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET to the server from the same private Google secret for Calendar consent. The web Lambda invokes the data Lambda through IAM. Neither a public data service nor a NAT gateway is required. The existing production provider stays active until cutover. Cognito login uses state, PKCE, nonce and issuer/audience/token-use validation. HTTP-only cookies hold the session. The PostgREST data endpoint must verify the same pool’s signing keys and client audience; update its JWKS on key rotation. Use `.token_use` as the role selector and `cognito_bridge.bind_cognito_owner` as the pre-request function. Apply `cognito-owners.sql` after restoring owner records and application roles. As the database operator, insert the single `(true, issuer, client_id)` configuration row in `cognito_bridge.pool` using the verified pool issuer and web client. To package the isolated data runtime, run `bash deploy/aws/package-data.sh "$POOL_ID" /private/path/data.zip`, then upload it by digest to the release bucket. The pinned ARM64 PostgREST binary, verified JWKS and RDS CA bundle ship together. Deploy `data.yaml` with the writer hostname, authenticator-only secret, app client, database security group and private network settings. Set a database-side idle session timeout for the authenticator to allow a frozen Lambda's dormant connections to close. Verify denied anonymous and foreign-owner reads before routing requests to this function.

The mapping checks the stable Google subject and verified email in the recovered identity record, then supplies the original UUID to the existing RLS policies. Workspace membership is checked on each protected operation. Acceptance requires real sign-in, existing owner access, cross-user and stale-write denial, separate Calendar consent, handling a newly invited identity, revoked sessions and owner QR sign-in. Install `cognito-qr.sql` after the owner bridge. QR uses a target-held PKCE verifier and the existing device approval, owner check, expiry and revocation records. Keep ADMIN_QR_ENABLED off during staging until a two-device login, revocation and a subsequent protected request have been verified.

## Restore production data

The protected GitHub database workflow includes a read-only `backup-for-aws` operation on main. It uses the existing source password and encryption/retention verification, with a separate migration key in the production-database environment. The matching key is held in the destination AWS account's SSM SecureString `/bart-site/migration/backup-key`. Previous backups use the original backup key. Keep the environment reviewer and main-only rules in place. Download only the site’s verified artifact and confirm its GitHub digest against the object checksum after placing it in private S3.

Restore a fresh export into an isolated database, compare records, sequences, ownership, roles, grants and row policies, then install the Cognito mapping. The Lightsail restore script requires a Supabase-initialized PostgreSQL image and its privileged operator; Aurora needs a restore rehearsed with its managed-service privileges. Maintain the original owner IDs, app grants, migration ledger and private chat encryption key. Exercise the data endpoint with the actual app, scheduled job and authorized operator tools. A copied encrypted archive alone does not establish a successful restore.

## Cutover and retirement

Export the complete Vercel DNS zone, including CAA, email, verification and wildcard records. Check the registrar delegation and DNSSEC before changing authority. Verify all answers on the AWS hosted zone and the certificate for both apex and www. Fence all source writers, take the final backup, compare against the AWS data, then switch the web records and verify public pages, Google login, private reads/writes, callbacks, cron and desktop/mobile behavior. If AWS has accepted writes, fence both sides and reconcile changes before a rollback. Keep domain registration current. Once the checks and recovery succeed, cancel the site’s Vercel and Supabase services and verify billing on each.

### Cancel the two subscriptions

1. Record the billing owner, current plan, latest invoice, renewal date, remaining add-ons, and other projects sharing each team or organization. Check whether the Supabase subscription was purchased through a marketplace. Protect unrelated projects and the Namecheap registration.
2. After AWS acceptance and a tested rollback copy, disable source deployments, scheduled invocations and integration callbacks. Check the old providers' traffic and write activity across the DNS TTL and a scheduled job run. Archive the deployment settings, DNS export, final backup checksum and billing evidence privately.
3. In the Supabase organization’s Billing settings, remove site-specific paid add-ons and use **Change subscription plan → Free** if the organization is dedicated to this site. For marketplace billing, complete the buyer-side cancellation at the listed marketplace. Verify the effective plan, remaining projects, and any final usage invoice. The dashboard downgrade is immediate. [Supabase subscription management](https://supabase.com/docs/guides/platform/manage-your-subscription). [Supabase billing FAQ](https://supabase.com/docs/guides/platform/billing-faq).
4. In the Vercel team's **Settings → Billing**, remove the site's paid add-ons and marketplace subscriptions, then use **Downgrade Plan → Hobby** for a dedicated Pro team. Verify the displayed effective date and renewal status. A team downgrade may remove other members or require a domain/store transfer. If the billing entity is shared, retire only this site's resources and record the shared charge separately. [Vercel Pro downgrade](https://vercel.com/docs/plans/pro-plan).
5. Record each provider's confirmation, effective date, final invoice or outstanding usage, and the next renewal amount. Recheck the public domain, Gmail login and an AWS-backed private save after retirement. Check the next billing statement for continued recurring charges. Use the providers’ self-service dashboards throughout.
